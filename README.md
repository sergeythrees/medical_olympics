# Clinical Cases — тестовое задание Full Stack Engineer (Eximion)

Мини-версия Medical Olympics: врач читает клинический кейс, выбирает диагноз и тактику и
получает баллы с разбором. Три части задания — один связный продукт:

```
[ Сырой текст кейса ]
         │
         ▼
[3] LLM-извлечение (DeepSeek/Gemini)
         │
         ▼
[ CaseIn (JSON) ] (та же схема)
         │
         ▼
[1] FastAPI + Postgres (нормализованная БД, скоринг в SQL)
         │
         ▼
[2] Next.js (RSC + клиентская форма ответа)
```

Один Pydantic-класс `CaseIn` ([backend/app/schemas.py](backend/app/schemas.py)) — это одновременно
тело `POST /cases`, JSON-схема для LLM ([schemas/clinical_case.schema.json](backend/schemas/clinical_case.schema.json))
и источник TypeScript-типов фронтенда (через OpenAPI). Черновик кейса от LLM валидируется теми же
правилами, что и кейс, присланный в API.


## Запуск

```bash
docker compose up --build
```

- http://localhost:3000 — фронтенд (4 демо-кейса уже в БД)
- http://localhost:8000/docs — Swagger API
- `POST /extract` (LLM) работает, если в `backend/.env` задан `DEEPSEEK_API_KEY` или Gemini (см. [backend/.env.example](backend/.env.example)); без ключа отвечает 503.

Тесты:

```bash
docker compose up -d db
cd backend && uv sync && TEST_DATABASE_URL=postgresql+psycopg://postgres:postgres@localhost:5432/cases_test uv run pytest
cd frontend && pnpm install && pnpm test && pnpm typecheck
```

Тестовая БД `cases_test` создаётся автоматически. Те же шаги — в [CI](.github/workflows/ci.yml).

## 1. Backend: FastAPI + PostgreSQL

### Схема данных

```
cases ─┬─< case_findings          (осмотр, анализы, ЭКГ, визуализация; порядок сохранён)
       ├─< answer_options         (kind = diagnosis | management, points от -10 до 10, объяснение)
       └─< submissions ─< submission_answers >─ answer_options
                                   (case_id, kind скопированы для составных FK)
```

Целостность обеспечивает сама БД, а не только API:

- **Ответ нельзя привязать к варианту из чужого кейса**: составной FK
  `submission_answers(option_id, case_id, kind) → answer_options(id, case_id, kind)` и
  `(submission_id, case_id) → submissions(id, case_id)`.
- **Не больше одного диагноза в ответе**: частичный уникальный индекс `… (submission_id) WHERE kind = 'diagnosis'`.
- **Одна попытка на участника** — `UNIQUE (case_id, participant)`: это соревнование, а не тренажёр; гонку двух одновременных запросов разрешает БД (→ 409).
- Уникальность вариантов без учёта регистра, CHECK на диапазоны, `ON DELETE CASCADE`.

Витальные показатели — колонки `cases` (1:1 с кейсом, отдельная таблица не добавила бы нормализации).

### Скоринг

Считается во view `submission_scores` (в миграции): одна агрегация с `FILTER` даёт `score`
(сумма баллов выбранных вариантов, вредные действия вычитают, пол — 0), `max_score`
(лучший диагноз + все показанные действия) и `diagnosis_correct`. Из этого же view читают
и результат ответа, и лидерборд (`RANK() OVER`), так что правило подсчёта в одном месте.

Пример (inferior STEMI): NSTEMI (+3) + аспирин (+5) + нитроглицерин (−5, гипотония при инфаркте ПЖ) = **3 / 28**.

### API

| | |
|---|---|
| `POST /cases` | создать кейс с ключом ответов (`CaseIn`); 422 при нарушении правил (ровно один правильный диагноз, уникальные варианты, хотя бы одно показанное действие) |
| `GET /cases`, `GET /cases/{id}` | кейс для участника — **без баллов и объяснений** (отдельная схема `CasePublic`, тест проверяет, что ключ не утекает) |
| `POST /cases/{id}/submissions` | принять ответ и вернуть разбор: баллы, правильный диагноз, пропущенные и вредные действия |
| `GET /submissions/{id}` | тот же результат повторно |
| `GET /cases/{id}/leaderboard` | рейтинг по кейсу |
| `POST /extract` | сырой текст → черновик `CaseIn` (задание 3) |

Миграции: `alembic upgrade head` / `downgrade base` (рабочий downgrade проверяется тестом).

## 2. Frontend: Next.js (App Router) + TypeScript

- **Server Components**: список кейсов и страница кейса загружаются на сервере (`src/lib/api.ts`,
  `server-only`). Текст кейса, витальные, результаты — чистый HTML без JS.
- **Клиентский остров** — только `AnswerForm`: выбор диагноза и действий, отправка, показ результата.
- **Отправка — через Server Action** ([actions.ts](frontend/src/app/cases/[id]/actions.ts)), а не `fetch` из браузера:
  URL backend не попадает в бандл, CORS не нужен, ошибки (409 «уже отвечал», 422, недоступность)
  превращаются в понятные сообщения.
- **Общие типы**: `pnpm gen:api` генерирует `api-schema.ts` из `backend/schemas/openapi.json`,
  клиент `openapi-fetch` типизирует пути, параметры и тела. Дрейф контракта ловится дважды:
  backend-тест проверяет, что `openapi.json` актуален, frontend-тест — что типы сгенерированы из него.
  Ручных дубликатов типов нет.
- 404 для несуществующего кейса, error boundary, `aria-live` для результата, тёмная тема.
- Тесты (Vitest + Testing Library): валидация формы, payload, рендер разбора, показ ошибки с сохранением ответов.

## 3. LLM-пайплайн: текст → структурированный кейс

[backend/app/extraction.py](backend/app/extraction.py). Провайдер выбирается по тому, какие
креды заданы (`make_llm`); код пайплайна от провайдера не зависит (`LLM` — протокол с одним методом):

| провайдер | как гарантируется формат | где |
|---|---|---|
| **DeepSeek** (`deepseek-flash`) | JSON mode + JSON-схема в системном промпте | на нём сделана оценка ниже |
| **Gemini** через **Vertex AI** или API key | `response_json_schema` — декодирование, ограниченное схемой | прод на GCP: по service account, без ключей |

1. JSON-схема для модели — `CaseIn.model_json_schema()`, `temperature=0`.
2. **Валидация Pydantic** — тем же классом, что и API. Правила, которые JSON-схемой не выразить
   (ровно один правильный диагноз, уникальность вариантов), проверяются здесь.
3. **Repair-цикл**: при невалидном JSON или нарушении правила модель получает свой ответ и точный
   текст ошибки; до 3 попыток, затем `502`. Для DeepSeek, у которого нет schema-constrained
   decoding, это основная гарантия формата.
4. Промпт требует не выдумывать отсутствующие данные (`null`), сохранять отрицания
   («ТГВ не подтверждён» — отрицательная находка, а не диагноз) и задаёт правило гранулярности
   находок — то же, по которому размечен golden-набор.

`POST /extract` возвращает черновик, но не сохраняет его: кейс с ключом ответов публикует автор
после проверки — LLM не должен единолично решать, что считать правильным ответом.

Проверено вживую на кейсе **не из golden-набора и на русском** (менингококкемия): `POST /extract`
за ~9 с вернул валидный кейс (десятичная запятая «39,4» → `39.4`, оба вредных действия → −5),
`POST /cases` его принял, страница отрисовалась во фронтенде — вся цепочка 3 → 1 → 2.

### Харнес оценки ([backend/evals](backend/evals))

Golden-набор — 4 кейса разных специальностей (ТЭЛА у беременной, нижний STEMI с поражением ПЖ,
САК, ДКА): сырой текст (`*.txt`, с сокращениями, смешанной записью единиц и отрицаниями) +
эталонная разметка (`*.json`). Эти же эталоны — демо-данные в БД.

```bash
cd backend
uv run python -m evals.run                                   # прогон модели → evals/runs/<run>/ (ответы + report.json)
uv run python -m evals.run --predictions evals/runs/<run>    # пересчёт метрик по сохранённым ответам, без LLM
```

| метрика | что ловит | gate |
|---|---|---|
| `schema_valid`, `attempts`, `latency_s` | надёжность и стоимость | `schema_valid = 1` |
| `correct_diagnosis` | правильный ли вариант получил 10 баллов | `= 1` |
| `management_polarity_errors` | **вредное действие оценено как показанное (или наоборот)** — соревнование начнёт награждать вред | `= 0` |
| `vitals_accuracy` | числа витальных показателей | `≥ 0.95` |
| `findings_coverage` | каждый факт эталона есть в какой-то находке модели (с учётом отрицаний), как бы модель ни разбила находки | `≥ 0.9` |
| `findings_grounded` | каждое число в находках модели есть в исходном тексте — галлюцинации без эталона | `= 1` |
| `finding_values_accuracy` | числа в значениях анализов (тропонин 180 ≠ 18) | `≥ 0.95` |
| `findings_precision / recall / f1` | структурное совпадение с разметкой 1:1 (чувствительно к гранулярности) | — |
| `diagnosis_options_recall`, `management_f1`, `management_points_exact` | полнота и баллы ключа ответов | — |

Раннер завершается с кодом 1, если gates не пройдены, — его можно ставить в CI на изменения
промпта/модели. Сами метрики покрыты unit-тестами (эталон против себя = 1.0; каждая порча эталона ловится).

**Результаты, `deepseek-flash`, 3 прогона** ([evals/runs](backend/evals/runs)):

| | DKA | STEMI | ТЭЛА | САК | итого |
|---|---|---|---|---|---|
| schema_valid / попыток | 1 / 1 | 1 / 1 | 1 / 1 | 1 / 1 | **3/3 прогона, без repair** |
| correct_diagnosis, polarity_errors | 1, 0 | 1, 0 | 1, 0 | 1, 0 | **ключ ответов без ошибок** |
| vitals, coverage, grounded, values | 1.00 | 1.00 | 1.00 | 1.00 | **1.00** |
| findings_f1 (структура) | 1.00 | 0.95–1.00 | 1.00 | 0.80 | **0.94–0.95** |
| latency, с | 7–8 | 6–13 | 6–7 | 7–10 | **6.7–9.6** |

Что харнес нашёл по дороге (и почему метрики такие, какие есть):

1. Первый прогон дал findings F1 0.80. Разбор расхождений показал, что почти все — **ошибки метрики**:
   синонимы («JVP» / «Jugular venous pressure», «GCS» / «Glasgow Coma Scale»). Добавлены словарь
   аббревиатур и сопоставление по содержательному значению находки.
2. Оставшиеся расхождения в DKA вскрыли **непоследовательность моей разметки**: газы крови в ТЭЛА —
   одна находка, в DKA — пять. Правило гранулярности записано явно и в промпт, и в разметку.
3. После этого САК «упал» до 0.58 recall: модель свела неврологический осмотр в одну находку —
   все факты на месте, отличается только разбиение. Вместо подгонки эталона под модель метрика
   разделена: `coverage` + `grounded` проверяют содержание (на них gate), F1 — структуру (информативно).

Ограничение: 4 кейса — это демонстрация харнеса, а не статистически значимое сравнение моделей;
`coverage` устойчив к объединению находок, но не к дроблению одной находки на части (это видно в precision).

## Допущения и что вне scope

- Нет аутентификации: участник — это имя в форме. В проде — идентификатор пользователя из auth,
  а уникальность попытки — по нему.
- Диагноз выбирается из вариантов, а не вводится свободным текстом: так скоринг детерминированный.
  Свободный ввод — следующий шаг (нормализация к вариантам через LLM с ручной апелляцией).
- Нет версионирования кейсов: правка кейса после первых ответов изменила бы чужие результаты.
  В проде — неизменяемые версии кейса, ответ ссылается на версию.
- 4 golden-кейса достаточно, чтобы показать харнес, но мало для статистически значимого сравнения
  моделей/промптов; набор надо растить вместе с реальными авторскими текстами.
